# 0002. 前端持有会话与对比任务的状态

- 状态：已采纳
- 日期：2026-10-14
- 相关：`web/src/pages/Chat.tsx`、`web/src/pages/Compare.tsx`、`server/api.mjs`

## 背景

对话与对比都是「持续产生增量、结束后才有完整结果」的长过程。有两种状态归属方式：

1. **服务端权威**：每个 token 都 PATCH 回服务端，服务端持有当前状态；
2. **前端权威**：前端持有运行中的状态，结束后整体落库。

流式场景下前者意味着每秒数十次写盘；后者在浏览器崩溃时会丢失未落库的最后一轮。

## 决策

**前端持有运行中的状态，服务端只在明确的落库点整体写入。**

- 对话：追加用户消息后立即 PUT 一次（保证提问不丢），流结束后再 PUT 完整会话；
- 对比任务：运行期间完全不落库，「保存记录」时才 POST 一条 Run 快照；
- 流式增量在前端用 `requestAnimationFrame` 合批刷新，避免每帧多次 re-render。

## 备选方案

- **token 级落库**：放弃——每秒几十次 JSON 重写，收益是「刷新页面能看到半个回答」，不值得。
- **仅内存不落库**：放弃——刷新即丢，评测结果无法复盘。
- **WebSocket 双向同步**：放弃——单机单人场景，SSE + 显式落库已经足够，引入连接状态管理反而更脆。

## 后果

- 正面：写盘次数从「每 token」降到「每轮」，`store.mjs` 的 250ms 防抖足以覆盖；
  对比任务可以随时中止而不留下半截脏数据。
- 负面：流式过程中刷新页面会丢掉正在进行的那一轮（已落库的提问保留）。
- 负面：状态逻辑集中在前端组件里，组件内的 `setState` 相对密集；
  `react-hooks/set-state-in-effect` 因此被降级为 warning（见 `eslint.config.js`）。
- 后续关注：若将来要支持多人协作或断线续传，需要改为服务端权威并引入会话订阅。
