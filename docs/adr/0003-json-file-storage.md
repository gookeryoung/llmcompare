# 0003. 用 JSON 文件而非数据库做持久化

- 状态：已采纳
- 日期：2026-10-14
- 相关：`server/store.mjs`

## 背景

需要持久化 6 类数据：模型配置（含 API Key）、会话、题库、题目、评测记录、设置。
典型数据量：几十个模型、几百道题、几百条评测记录、几十个会话。
使用者是单个开发者，本机运行，没有并发写入需求。

同时有一个强诉求：**API Key 存在哪里必须一眼可见、可备份、可手工编辑**。
这是个人工具，透明度比查询能力重要。

## 决策

**每类数据一个 JSON 文件，放在 `data/` 下；写入采用「防抖 250ms + 临时文件原子替换」。**

- `models.json` / `conversations.json` / `banks.json` / `questions.json` / `runs.json` / `settings.json`
- 写入串行化（每个集合一条 promise 链），避免两次写并发导致内容交错；
- 进程退出时 `flushAll()` 兜住尚未落盘的防抖任务；
- 服务端不引入任何运行时依赖。

## 备选方案

- **SQLite（`node:sqlite`）**：放弃——本可零依赖，但表结构/迁移会给这个规模的项目增加维护面，
  而且使用者无法用文本编辑器直接改一条模型配置。
- **lowdb / better-sqlite3 等第三方库**：放弃——为了「存 6 个 JSON」引入运行时依赖，
  与「服务端零依赖」的整体取舍冲突。
- **浏览器 localStorage**：放弃——密钥会落到浏览器，且无法在服务端代理上游请求。

## 后果

- 正面：`data/` 目录直接复制就是完整备份；出问题时人眼可读；服务端零依赖使 Docker 运行层不需要 `node_modules`。
- 负面：集合全量重写，数据量上千条后单次写入成本上升；当前规模（<1MB）无感，
  超过约 10MB 就需要改成分片或迁移到 SQLite。
- 负面：没有事务，跨集合操作（如删除题库级联删题目）不是原子的，崩溃窗口内可能留下孤儿题目。
- 后续关注：评测记录是增长最快的一类，若单文件超过数 MB，应优先把它拆成「索引 + 单条文件」。
